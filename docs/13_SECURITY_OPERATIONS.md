# 보안과 운영 기준

이 시스템은 건강 관련 상담정보와 발 이미지를 다루므로 실제 환자 데이터 수집 전 운영 주체의 개인정보·외부 AI 사용 정책을 확정해야 합니다. 본 문서는 기술 기본선이며 법률·의료 자문을 대체하지 않습니다.

## 접근·데이터 보호

- 관리자 공개가입을 만들지 않고 최초 계정은 운영자가 생성합니다. 비밀번호 검증·해시는 Supabase Auth에 맡기고 업무 DB에 비밀번호 해시를 따로 두지 않습니다. 로그인 제한·세션 만료·비활성화는 아래 [직원 인증과 계정 상태](#직원-인증과-계정-상태)를 따릅니다.
- 모든 API와 파일 조회에서 기관·담당자·역할·삭제·확정 상태를 서버에서 검사합니다. 화면에서 버튼을 숨기는 것만으로 권한을 구현하지 않습니다.
- HTTPS를 사용합니다. 업무 테이블은 Data API로 자동 노출하지 않고(P19) RLS를 켠 기본 차단으로 시작해 필요한 접근만 마이그레이션에서 GRANT·정책으로 엽니다. 브라우저가 Data API로 기관·역할·담당자·삭제·확정 상태를 바꿀 수 있는 경로를 만들지 않습니다.
- RLS를 우회하는 서버 권한(secret·service_role 키, DB 직접 연결)을 쓰는 함수 경로는 요청자 인증·기관·역할·담당자 검사를 코드에서 먼저 수행합니다. 우회 권한을 쓰는 코드는 실행환경 진입점의 연동 모듈에만 둡니다.
- 파일 확장자가 아니라 실제 MIME, 크기, 픽셀, 디코딩 성공을 검사하고 임의 파일명으로 저장합니다. SVG·실행파일은 받지 않습니다.
- 공개 설정과 서버 비밀값을 나눕니다. 웹에는 `VITE_` 공개값(API 주소, Supabase URL·publishable 키)만 두고, secret·service_role 키, DB 접속 정보, AI 공급자 키는 Supabase 함수 비밀값(`supabase secrets`)으로만 주입합니다. Git·브라우저 번들·로그에 넣지 않으며 웹 빌드·배포 명령마다 `scripts/check-web-bundle.mjs`로 검사합니다. 이 검사는 형식이 알려진 키(`sb_secret_`, role이 `service_role`인 JWT, `sk-` 형식)와 비밀값으로 보이는 `VITE_` 이름만 찾으므로 1차 방어는 서버 비밀값을 `VITE_` 변수로 만들지 않는 것입니다. 발견 시 키 원문·JWT 내용은 출력하지 않습니다. JWT는 role 확인을 위해 내용만 읽으며 서명을 검증하지 않습니다(인증 판단과 무관).
- AI 전송 전에 이름·전화·고객번호를 제거합니다. 이미지 전송 여부와 보관 정책은 O07에 따릅니다.
- 개인정보를 로그에 남기지 않고 requestId, 행위자, 엔터티 ID, 결과 코드 중심으로 기록합니다.

## 직원 인증과 계정 상태

Supabase Auth는 이메일·전화 등으로 로그인하며 아이디(사용자 이름) 로그인을 기본 제공하지 않습니다. 기존 정책(아이디 로그인, 관리자 계정 발급, 관리자 비밀번호 재설정, 공개가입·이메일 발송 없음)과의 차이와 대응은 다음과 같습니다.

| 기존 정책 | Supabase Auth 기본 | MVP 대응(P20, O13 결정 전) | 정책 변경 필요 여부 |
| --- | --- | --- | --- |
| 아이디 + 비밀번호 로그인 | 이메일(또는 전화) + 비밀번호 | 로그인 아이디를 정규화(소문자, 허용 문자 제한)해 발송하지 않는 내부 인증 이메일(예: `<아이디>@<운영 도메인의 비발송 하위 도메인>`)로 만들고 로그인 화면은 아이디만 받음 | 아이디 변경 시 인증 이메일도 서버에서 함께 변경. 실제 이메일 로그인으로 바꿀지는 O13 |
| 관리자 계정 발급, 공개가입 없음 | 가입 허용이 기본 | `enable_signup = false`. 관리자 요청을 함수가 검사한 뒤 Admin API로 생성(`email_confirm` 처리, 메일 미발송) | 없음 |
| 관리자 비밀번호 초기화, 이메일 발송 없음 | 재설정 메일 흐름 | 함수가 관리자 권한 확인 후 Admin API로 임시 비밀번호 설정, 업무 DB의 `passwordChangeRequired` 표시로 다음 로그인 때 변경 유도 | 강제 변경 방식은 Supabase 기본 기능이 아니므로 O13에서 확인 |
| 비활성화 즉시 세션 해제(P11) | 접근 토큰은 만료 전 취소 불가(기본 1시간) | 아래 비활성화 처리 | "즉시"는 업무 API 기준의 설계 목표이며 T03에서 검증. Supabase 다른 경로는 토큰 만료까지 남을 수 있음 |

모든 직원 경로의 공통 원칙: 업무 API는 JWT 서명·만료만 믿지 않고 요청마다 `authUserId → app_users`를 조회해 현재 활성 상태·역할·기관을 확인합니다. JWT의 역할 클레임만으로 권한을 판단하지 않습니다. 함수 게이트웨이 JWT 검사를 끈 상태(`verify_jwt = false`)이므로 직원·공개 질문지·내부 작업 경로의 인증 구현은 T03·T07·T10A의 필수 조건이며, 인증 검사가 없는 경로를 추가하지 않습니다.

**계정 비활성화(로그인 차단과 세션 정리)**

1. 업무 DB `app_users.status`를 비활성으로 바꾸고 감사 기록을 남깁니다(원자적).
2. Admin API로 해당 인증 사용자를 차단(`ban_duration`)해 새 로그인을 막고 남은 세션을 정리합니다. 차단이 기존 세션·갱신 토큰까지 끊는지와 다른 사용자의 세션을 지우는 방법(Admin API 또는 `auth.sessions` 정리 DB 함수)은 공식 문서에 명시되지 않아 **검증 전까지 미확인**이며 T03에서 시험합니다.
3. 차단 효과와 관계없이 업무 API는 위 공통 원칙으로 비활성 계정의 요청을 거부합니다.

**역할 변경(현재 권한 반영)**

- 역할 변경(예: 관리자 → 시술자)은 계정을 차단(ban)하거나 로그인을 막지 않습니다. 업무 DB `app_users.role`과 감사 기록만 바꿉니다.
- 다음 요청부터 업무 API가 DB의 현재 역할로 판단하므로 관리자 기능은 거부되고, 시술자에게 허용된 업무(기관 내 조회, 담당 상담 수정 등)는 기존 토큰으로 계속 쓸 수 있어야 합니다.
- 기존 접근 토큰에 남은 역할 정보는 권한 판단에 쓰지 않습니다. 필요하면 다시 로그인하도록 안내할 수 있지만 권한 반영의 전제 조건이 아닙니다.

브라우저가 업무 데이터에 Data API로 직접 접근하지 않고 Storage에 브라우저용 정책을 두지 않으므로(P19) 남은 접근 토큰으로 할 수 있는 일은 Auth 자체 기능(자기 정보 조회 등)으로 제한되도록 설계합니다(T02·T09에서 검증). Storage 서명 URL은 함수가 권한을 확인한 뒤에만 짧게 발급하므로 비활성 계정은 새 URL을 받지 못하지만, 이미 발급한 URL은 만료까지 유효합니다(만료 시간을 짧게 둠).

검증 계획(T03, [검수](14_ACCEPTANCE_TESTS.md) AT-23~25): 비활성화 직후 기존 접근 토큰으로 업무 API 호출이 거부되는지, 토큰 갱신이 거부되는지(차단 효과 확인), 역할 변경 직후 관리자 API는 거부되고 시술자 업무는 계속 가능한지, 로그인 아이디 대소문자·공백 정규화, 내부 인증 이메일이 Supabase 이메일 검증을 통과하고 메일이 발송되지 않는지 로컬 Supabase와 스테이징에서 확인합니다. 로그인 식별자와 임시 비밀번호 정책은 O13 결정 전입니다.

## 비공개 파일

- 버킷은 비공개이며 `storage.objects`에 브라우저용 정책을 두지 않아 기본 차단합니다. 파일 메타데이터에는 저장소 구분·버킷·객체 경로·형식·크기·해시를 저장하고 공개 URL이나 만료되는 서명 URL을 기준 데이터로 저장하지 않습니다.
- 업로드: 함수가 업무 권한(담당자·관리자, 또는 유효한 질문지 토큰의 허용 유형)을 확인하고, 상담 ID와 서버가 만든 무작위 객체 경로, 허용 형식·최대 크기를 정해 서명 업로드 URL을 발급합니다. 서명 업로드 URL은 Supabase 기준 2시간 유효이며 크기·형식은 버킷 설정(`file_size_limit`, `allowed_mime_types`)과 업로드 완료 검사로 제한합니다. 완료 요청에서 객체 존재·크기·형식·해시를 확인한 뒤에만 `READY`로 바꿉니다.
- 조회: 함수가 권한을 확인한 뒤 짧게 만료되는 서명 URL(제안 5분)을 발급합니다. 발급한 URL은 DB·로그에 저장하지 않습니다.
- 원본 이미지는 덮어쓰지 않고, 교체는 새 객체와 새 메타데이터 행으로 남깁니다.

## 공개 질문지 링크

토큰 원문은 DB에 저장하지 않고 해시를 저장합니다. 추측하기 어려운 길이를 사용하고 만료·폐기·제출 상태를 서버에서 검사합니다. 검색엔진 색인을 막고 속도 제한을 둡니다. 토큰 하나로 해당 상담 질문지 외 환자정보·과거회차·파일을 조회할 수 없습니다.

- 직원 경로(인증 토큰)와 공개 질문지 경로(`/public/questionnaires/:token`)를 함수 안에서 분리합니다. 공개 경로는 직원 인증을 받지 않고, 직원 경로는 질문지 토큰을 받지 않습니다.
- 질문지 토큰으로는 그 상담의 질문 정의 조회, 원자적 제출, 허용된 사진 업로드 요청만 할 수 있습니다.
- 만료·재발급·폐기·중복 제출은 서버에서 검사합니다. 재발급은 이전 토큰을 폐기하고, 제출은 한 번만 저장합니다.
- 토큰 원문은 로그·감사 기록·오류 메시지에 남기지 않습니다. 현재 검증된 범위는 **`packages/api-core`가 직접 남기는 로그**뿐입니다(경로 원문 대신 경로 이름만 기록, 테스트 있음).
- 플랫폼 기록은 별도 검증 대상입니다. Supabase 공식 문서에 따르면 API 게이트웨이 로그는 요청 경로(Pathname)로 검색할 수 있고, Edge Function 호출 기록은 헤더·본문을 포함한 요청/응답 데이터를 담습니다. 따라서 질문지 토큰이 경로·헤더·본문 어디에 있든 플랫폼 기록에 남을 수 있으며, **토큰을 헤더나 본문으로 옮긴다고 자동으로 안전해지지 않습니다.** 웹 링크(`/q/:token`)도 Cloudflare 요청 기록·브라우저 `Referer`로 전달될 수 있어 함께 확인합니다.
- 검증 방법(T07, 로컬 Supabase → 스테이징): 합성 토큰으로 질문지 조회·제출·실패(만료·폐기) 요청을 보낸 뒤 Studio 로그 탐색기(API 게이트웨이·`function_edge_logs`·`function_logs`·Postgres·Storage 로그)와 Cloudflare 요청 기록에서 그 토큰 문자열을 검색합니다. 남는 경우 토큰 전달 방식(짧은 수명 교환 토큰 등), 로그 보존 기간·열람 권한, `Referrer-Policy`를 T07에서 결정합니다. 실제 유출은 아직 확인되지 않았으며 원격 환경 검증은 미실행입니다.
- 링크 유효 72시간·제출 1회(P08)는 제안값이며 운영 확인 전입니다.

## 감사 대상

로그인 성공·실패, 계정 상태 변경, 환자·상담 핵심정보 변경, 링크 발급·폐기, 제출, 파일 등록, 발도장·AI 실행, 최종확정·개정, 삭제를 기록합니다. 민감 답변 원문과 비밀값은 감사 metadata에 복사하지 않습니다.

## 백업·복구

운영 DB 자동백업, 이미지 객체 버전·수명 정책, 배포 전 DB 스냅샷, 마이그레이션 롤백 또는 forward-fix 절차를 제안합니다. 보관기간·복구 목표·비용은 O07·O08에서 확정합니다. 백업 존재 여부만 보지 않고 스테이징에 복구 시험을 수행합니다.

## 배포 기준

Vue 정적 자산은 Cloudflare Workers Static Assets(정적 전용), 업무 API는 Supabase Edge Functions, 업무 데이터는 Supabase PostgreSQL, 이미지는 Supabase Storage 비공개 버킷에 배포합니다(D25). 개발·스테이징·운영의 Supabase 프로젝트와 비밀값을 분리하고 로그·오류·비용 알림을 설정합니다. DB 변경은 `supabase/migrations`로만 반영합니다. GitHub 자동배포 자격증명은 대상 계정과 프로젝트로 권한을 최소화합니다.

실제 Cloudflare·Supabase 원격 자원 생성은 별도 허용과 계정·비용·데이터 위치 요구 확인(O08) 후 수행합니다. 계정 비밀번호·MFA 복구값·API 토큰·서비스 키 원문을 채팅이나 저장소에 전달하지 않습니다.

*2026-09-22 기준(대체됨)*: Workers Assets·Workers API·D1·R2.

## 운영 전 체크

동의·보유·파기·외부처리 정책 승인, 관리자·운영 담당자 지정, 계정회수 절차, 도메인·인증서, 백업·복구시험, 경보 수신처, 취약점·의존성 점검, 스테이징 검수, 지원·장애연락 절차가 필요합니다.
