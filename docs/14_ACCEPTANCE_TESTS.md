# 검수 기준과 테스트 시나리오

## 검수 원칙

기능은 실제 저장된 데이터와 권한으로 검증합니다. 목업·하드코딩 응답·미구성 분석기는 구현 완료로 인정하지 않습니다. 보류 기능은 합의되지 않았음을 명확히 표시하면 그 외 MVP 검수를 진행할 수 있습니다.

## 핵심 시나리오

| AT-23 | 계정 비활성화 후 기존 토큰 | 비활성화 직후 이전 접근 토큰으로 업무 API·파일 URL 발급 거부, 토큰 갱신·재로그인 거부 |
| AT-24 | 역할 변경 후 기존 토큰 | 관리자→시술자 변경 직후 관리자 API는 거부, 시술자에게 허용된 업무(기관 내 조회·담당 상담 수정)는 같은 토큰으로 계속 가능, 계정 차단(ban)·로그인 차단 없음(JWT 클레임이 아닌 DB 현재 역할 기준) |
| AT-25 | 아이디 로그인 매핑 | 아이디 대소문자·공백 정규화, 메일 미발송, 공개 가입 차단, 업무 DB에 비밀번호 해시 없음 |
| AT-26 | 직접 DB API 우회 | 직원·익명 키로 Data API·Storage API를 직접 호출해 다른 기관 데이터 조회, 역할·담당자·삭제·확정 상태 변경, 비공개 파일 조회가 모두 거부 |
| AT-27 | 다른 기관·권한 없는 파일 | 다른 기관·담당 외 사용자에게 서명 URL 미발급, 객체 경로 추측으로 조회 불가 |
| AT-28 | 분석 작업 중단 복구 | 실행 중 중단된 작업이 임대 만료 후 회수되고, 늦게 끝난 이전 실행이 새 결과를 덮지 않음, 회수에 따른 재선점도 재시도 횟수에 포함되어 상한 후 `FAILED` |
| AT-29 | 외부 호출 결과 불명 | 응답 유실 시 자동 재호출 없이 `OUTCOME_UNKNOWN`, 담당자 확인 후 새 시도 |
| AT-30 | 최종확정 원자성 | 권한·입력 버전 비교·확정본 생성·감사 기록 중 하나라도 실패하면 전부 취소, 오래된 분석으로 확정 거부 |
| AT-31 | 외부 전송 전 중단 | `dispatchState=NOT_SENT`에서 멈춘 작업은 임대 만료 후 다시 선점·실행되고 외부 호출은 한 번만 발생(mock 공급자 호출 수로 확인) |
| AT-32 | 외부 전송 직후 중단 | `SENDING`이 기록된 뒤 멈춘 작업은 공급자 확인 수단이 없으면 `OUTCOME_UNKNOWN`, 자동 재호출 0회 |
| AT-33 | 응답 수신 후 DB 저장 전 중단 | 응답을 받았으나 저장 전에 멈춘 작업도 `OUTCOME_UNKNOWN`, 자동 재호출 0회, 이후 늦은 저장 시도는 `lockToken` 불일치로 반영 안 됨 |
| AT-34 | 입력 수정과 최종확정 동시 요청 | 둘 중 하나만 먼저 반영되고, 확정본은 확정 시점의 입력 버전과 일치. 확정 뒤 반영된 수정은 새 개정 대상이며 오래된 입력으로 확정되지 않음 |
| AT-35 | 최종확정 중복 요청 | 같은 확정 요청 두 번(더블클릭·재전송)에도 확정본·감사 기록이 하나만 생기고 두 번째는 기존 결과 또는 충돌 응답 |
| AT-36 | 권한·담당자 변경과 확정 경합 | 담당자 변경·역할 강등·비활성화가 먼저 반영되면 이전 담당자의 확정은 트랜잭션 안의 재확인으로 거부 |
| AT-37 | 확정본·감사 저장 실패 | 확정본 또는 감사 기록 저장을 실패시키면 상담 상태·확정본·감사가 모두 이전 상태로 남음 |
| AT-38 | 중복 제출과 수동 재시도 | 같은 분석 요청 키의 중복 요청은 기존 작업 반환, `OUTCOME_UNKNOWN` 뒤 담당자 확인 재시도는 새 시도·`retryOf`·확인자 기록 |
| AT-39 | 플랫폼 로그의 질문지 토큰 | 합성 토큰으로 조회·제출·실패 요청 후 API 게이트웨이·함수·DB·Storage 로그와 Cloudflare 요청 기록에서 토큰 문자열이 검색되지 않음. 검색되면 T07에서 전달 방식·보존·열람 권한 대응을 결정 |
| AT-40 | 함수 실행환경 | 로컬 `functions serve`(T02 착수 시)에서 `supabase/functions` 밖 공용 코드를 import한 함수가 health를 응답. 원격 번들·배포(T18)에서 같은 확인 |

## 자동 테스트 최소선

- unit: 문항 분기, `없음` 상호배제, 권한 규칙, 상태전이, 입력 해시, 오래됨 판정, AI schema.
- API integration(로컬 Supabase): 로그인, 기관 격리, RLS·Data API 직접 호출 차단, 제출 원자성, 업로드 권한, 낙관적 잠금, 논리삭제, 작업 선점·회수.
- E2E: AT-03~06 중 대표 흐름, 상담 저장, AI mock 성공·실패, 최종확정, 관리자 삭제.
- migration: 빈 DB와 이전 스키마 양쪽에서 적용, seed는 합성 데이터만 사용.

## MVP 전체 흐름 검수 목표

로그인 → 환자 등록 → 상담 생성 → 질문지 링크 발급·제출 → 이미지 업로드 → 분석 요청(미구성·mock) → 결과 검토 → 최종확정을 실제 저장 데이터로 한 번에 통과해야 MVP 기능 완료입니다. 함께 확인할 항목: 다른 기관·권한 없는 사용자의 데이터·이미지 차단(AT-10·26·27), 계정 비활성화 후 기존 토큰 차단(AT-23), 직접 DB API 우회 차단(AT-26), 중복 제출·동시 수정(AT-08·19), 분석 실패·재시도·중단 복구(AT-12·16·28·29·31~33·38), 오래된 분석 결과의 확정 방지와 확정 경합(AT-15·30·34~37), 플랫폼 로그의 토큰(AT-39). 보류 중인 임상 조건(O04·O05)을 통과시키기 위해 임의 기준을 만들지 않습니다.

## 검증 단계 구분

결과를 보고할 때 다음 단계를 나눠 적고, 실행하지 않은 단계를 통과로 쓰지 않습니다.

1. 정적 검사·mock 테스트: 타입 검사(환경변수 타입 검사 파일 포함), 린트, Vitest(웹·계약·서버 코어), 스크립트 테스트(번들 비밀값 검사, ESLint 경계 허용·차단 사례), Deno 타입 검사, 웹 빌드·번들 비밀값 검사.
2. 로컬 Supabase 통합: `npx supabase start`(Docker 필요), 마이그레이션·RLS·Auth·Storage·함수 로컬 실행.
3. 원격 Supabase·Cloudflare 스테이징: 별도 승인과 O08 이후.

## 분석 검수 게이트

샘플 검증 전에는 업로드·상태·어댑터 계약만 검수합니다. 실제 정량값과 스크리닝은 O01·O02에서 확정한 입력유형, 기준값, 독립 검증 사례, 허용오차, 실패기준으로 별도 검수합니다. 정확도가 부족한 항목은 지원목록에서 제외하거나 수동확인으로 낮춥니다.

AI `CARE_SUPPORT`는 승인 사례에서 누락·금지표현·근거·위험 평가를 통과하고 시술자가 승인한 후 운영합니다. 테스트 수치와 합격선은 사례 확보 후 문서에 추가합니다.

## 완료 정의

코드·DB 마이그레이션·환경 예시·테스트·관련 문서가 함께 갱신되고, 보안 차단 이슈가 없으며, 담당자가 스테이징에서 핵심 시나리오를 확인해야 완료입니다. 화면만 존재하거나 API가 더미 데이터를 반환하면 완료가 아닙니다.
